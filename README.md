# Original Company Home

مشروع Home مستقل مبني من الصفر بـ Next.js وReact وTypeScript، مع الحفاظ على التصميم المرجعي الموجود في `home.html` داخل المشروع الأصلي.

## Stack

- Next.js App Router
- React + TypeScript
- Tailwind CSS v4
- Firebase Auth / Firestore CMS
- Supabase Storage media library
- React Hook Form + Zod
- Vitest
- next-intl (Arabic / English)
- Firebase Admin + Web Push

## Local Setup

1. انسخ القيم من `.env.example` إلى `.env.local`.
2. شغل:

```bash
npm run dev
```

## Service Readiness

```bash
npm run check:services
npm run check:services -- --online
npm run check:services -- --production
```

الفحص الأول محلي: يتحقق من وجود الإعدادات، وصحة ملف Service Account وتطابق المشروع، وتطابق مفاتيح Web Push، ومتطلبات رابط الموقع. لا يطبع المفاتيح أو محتويات الملفات. `--online` يضيف قراءة فعلية من Firestore وFirebase Authentication وSupabase Storage، ويتحقق من وجود دور أدمن نشط، بدون تعديل بيانات أو حسابات أو إنشاء bucket. هذا يثبت اتصال القراءة فقط؛ تسجيل الدخول والحفظ وتسليم Push يحتاج اختبارات مستقلة. النتيجة FAIL تُرجع exit code 1.

لإكمال Firebase على هذا الجهاز، نزّل ملف JSON لحساب الخدمة من Firebase Console: Project settings > Service accounts > Generate new private key، واحفظه محليًا خارج `public` و`src`. يمكن وضعه في `.secrets/firebase-service-account.json` المستثنى من Git، ثم تحديد مساره عبر `GOOGLE_APPLICATION_CREDENTIALS` في `.env.local`. لا تلصق المفتاح في المحادثة أو ترفعه إلى المستودع. على الاستضافة استخدم سرًا محميًا أو هوية خدمة بدل تضمين الملف في حزمة الموقع. [تعليمات Firebase الرسمية](https://firebase.google.com/docs/admin/setup#initialize_the_sdk_in_non-google_environments).

بعد إعداد حساب الخدمة: أعد تشغيل السيرفر، أنشئ حساب Firebase Authentication للأدمن وحدد `websites/originalcompany/users/{uid}` بالقيم `role: "admin"` و`active: true`، ثم اختبر تسجيل الدخول والحفظ وتفعيل إشعارات الجهاز. جدولة إعادة إرسال الإشعارات وإذن الجهاز مطلوبة أيضًا؛ صلاحية حساب الخدمة وحدها لا تضمن وصول Push.

## Website Isolation

كل بيانات الموقع الجديد تحت الوثيقة `websites/originalcompany`. أسماء المجموعات المذكورة لاحقًا نسبية لهذا المسار، بما فيها المنتجات والمحتوى والرسائل والأدوار واشتراكات الإشعارات. لا يقرأ الموقع منتجات النظام القديم ولا يعدّلها، ولا تمنح أدوار `users/{uid}` القديمة صلاحية دخول لوحة الموقع. Firebase Authentication مشترك، لكن صلاحية إدارة الموقع مستقلة.

```bash
npm run setup:site
npm run setup:site -- --apply
```

الأمر الأول يفحص عدد منتجات الموقع دون تعديل. `--apply` يستورد المنتجات الأربعة والمحتوى الأصلي مرة واحدة دون استبدال سجلات موجودة، ويجهز bucket الصور إن كان غائبًا. لا ينشئ حسابات ولا يغير أدوار مستخدمين أو بيانات النظام القديم.

## Products And CMS

- `/`: منتجات مربعة، أربعة أعمدة للديسكتوب وعمودان للموبايل، بحد أقصى صفين. زر عرض جميع المنتجات يفتح `/products`.
- `/products`: الكتالوج مع الناف بار والبحث والتصنيف والترتيب وتقسيم الصفحات. لكل منتج صفحة `/products/[slug]` وصور وتفاصيل. لا يوجد سعر أو زر طلب المنتج؛ عدد القطع الافتراضي 24 وقابل للتعديل.
- `/admin`: ملخص المنتجات والرسائل وآخر الرسائل. استيراد المحتوى الأصلي عملية اختيارية لا تستبدل البيانات الموجودة، ومحمية من التكرار.
- `/admin/products`: بحث وفلاتر وترتيب وإضافة وتعديل وحذف مع تأكيد، نشر وإخفاء، ترتيب العرض، وعدد القطع. الأسماء والأوصاف والتصنيفات والمواصفات تدعم العربية والإنجليزية. رابط المنتج فريد ومحجوز بمعاملة Firestore.
- `/admin/content`: تعديل Hero والمزايا والمصنع والناف بار والفوتر والتواصل ونصوص قسم المنتجات وترتيب الأقسام وإظهارها. إعدادات التصميم مثل تعتيم Hero محدودة لمنع كسر التصميم.
- `/admin/branches` و`/admin/socials`: إضافة وتعديل وحذف وترتيب وتفعيل الفروع والروابط.
- `/admin/settings`: هوية الموقع والشعار ومعلومات التواصل والعنوان وSEO واللغة البديلة عند عدم دعم لغة الجهاز.
- `/admin/media`: مكتبة الصور ورفع JPG/PNG/WebP بحد 5 MB. يتحقق السيرفر من محتوى الصورة وأبعادها، وليس اسم الملف فقط. يتم منع حذف صورة مرتبطة بمحتوى أو منتج.

Firestore هو مصدر المحتوى (`products`, `productSlugs`, `siteContent/main`, `media`). Supabase يحتفظ بملفات الصور فقط. المتغير `SUPABASE_MEDIA_BUCKET` يحدد الـ bucket، والافتراضي `site-media`. ينشئه السيرفر عند أول رفع إن لم يكن موجودًا؛ يجب أن يكون عامًا للقراءة، والرفع والحذف عبر السيرفر بصلاحية الأدمن فقط. لا تضف سياسات كتابة عامة. لا يصل مفتاح Supabase السري إلى المتصفح.

الحفظ يحدّث cache الصفحات العامة فورًا. عند غياب بيانات Firebase Admin، يعرض الموقع المحتوى الأصلي للمعاينة فقط؛ لا يتم ادعاء نجاح الحفظ ولا فتح لوحة الإدارة. مع إعداد Firebase، تُقرأ المنتجات من قاعدة البيانات، والقائمة الفارغة تبقى فارغة حتى يتم إدخال منتجات أو استيراد المحتوى.

## Languages

أول زيارة تعتمد على `Accept-Language` من المتصفح. يتم اختيار العربية أو الإنجليزية حسب ترتيب تفضيلات الجهاز، واللغة المحددة في إعدادات الموقع بديل عند عدم توفر لغة مدعومة. اختيار اللغة من القائمة يُحفظ في cookie لمدة سنة ويتقدم على لغة الجهاز. اتجاه الصفحة والنموذج ورسائل التحقق وبيانات المنتجات تتغير مع اللغة. حقل الهاتف يبقى بمحاذاة اليمين أثناء الكتابة بالعربية.

## Admin And Contact Messages

لإضافة حساب Firebase Authentication موجود إلى إدارة الموقع، استخدم الأمر التالي للمراجعة فقط، ثم أضف `--apply` لتفعيل الدور. يجب تحديد البريد المقصود صراحةً. الأمر لا ينشئ حسابات، ولا يغير كلمة المرور أو حالة حساب معطّل أو أدوار الأنظمة الأخرى.

```bash
npm run setup:admin -- --email admin@example.com
npm run setup:admin -- --email admin@example.com --apply
```

- الدخول: `/login`، ثم `/admin`، والرسائل داخل `/admin/messages`.
- يتم التحقق من جلسة Firebase ومن `websites/originalcompany/users/{uid}` عند كل قراءة إدارية وكل عملية حساسة. يجب أن تحتوي الوثيقة على `role: "admin"` و`active: true`.
- فعّل Email/Password في Firebase Authentication وأنشئ حساب الإدارة من Firebase Console، ثم أضف وثيقة صلاحياته باستخدام UID الحقيقي.
- يلزم Firebase Admin على السيرفر. إعدادات `NEXT_PUBLIC_FIREBASE_*` وحدها لا تكفي. عيّن `FIREBASE_ADMIN_CLIENT_EMAIL` و`FIREBASE_ADMIN_PRIVATE_KEY` في `.env.local` من Service Account لنفس المشروع، أو عيّن `GOOGLE_APPLICATION_CREDENTIALS` لمسار ملفه. على استضافة Google التي تملك هوية خدمة، استخدم `FIREBASE_USE_APPLICATION_DEFAULT=true`.
- لا تضع مفتاح Firebase Admin في متغير يبدأ بـ `NEXT_PUBLIC_`، ولا ترفعه إلى Git.
- قواعد `firestore.rules` تمنع الوصول المباشر من Firebase Client إلى كامل `websites/originalcompany`، حتى للحساب المسجل. القراءة العامة والحفظ يمران عبر السيرفر، والإدارة تتحقق من الجلسة والدور. القواعد تحافظ على السياسة السابقة خارج نطاق الموقع؛ لا تعتبرها تأمينًا للأنظمة الأخرى. انشرها من Firebase Console أو باستخدام `firebase deploy --only firestore:rules --project YOUR_PROJECT_ID` بعد مراجعة القواعد المنشورة. وجود الملف محليًا لا يعني نشره. `npm run check:services -- --online` يفحص منع قراءة رسائل الموقع دون تسجيل دخول؛ لا تستقبل رسائل حقيقية إذا فشل هذا الفحص.
- الرسالة والطلب الخاص بإشعارها يحفظان في transaction واحدة داخل `contactMessages` و`notificationOutbox`. يمنع تكرار الإرسال أكثر من خمس مرات لنفس الرقم خلال عشر دقائق. أضف حدود طلبات على مستوى الاستضافة للمواقع ذات الزيارات العالية.
- البريد الإلكتروني حقل إلزامي مباشرة تحت الاسم مع تحقق في المتصفح والسيرفر. الأدمن يشاهد الاسم والبريد والرقم والنص والتاريخ، ويغير الحالة إلى جديدة أو مقروءة أو تم الرد، ويمكنه الاتصال أو فتح واتساب أو رابط البريد.

## Background Notifications

1. شغّل `npm run setup:push` مرة واحدة. يولّد مفاتيح Web Push وسر جدولة إعادة المحاولة محلياً ويحافظ على المفاتيح الموجودة. عدّل `VAPID_SUBJECT` إلى عنوان تواصل الشركة الفعلي.
2. أعد تشغيل السيرفر بعد ضبط البيئة. على الاستضافة انقل المتغيرات إلى إعدادات السيرفر وأعد البناء لأن المفتاح العام يدخل في حزمة المتصفح.
3. افتح صندوق الرسائل بحساب أدمن واضغط تفعيل الإشعارات، ثم وافق على إذن المتصفح. كل جهاز يحتاج تفعيلًا منفصلًا. زر الإشعار التجريبي يختبر وصول الإشعار لذلك الجهاز.
4. السيرفر يرسل الإشعار فور حفظ الرسالة، و`public/sw.js` يعرضه حتى عند إغلاق صفحة الموقع. الضغط عليه يفتح الرسالة؛ عند انتهاء الجلسة يطلب الدخول أولاً.
5. جدولة طلب `POST /api/notifications/retry` كل دقيقة مع `Authorization: Bearer <NOTIFICATION_CRON_SECRET>` تعيد إرسال الطلبات المعلقة. يوجد قفل لخمس دقائق لمنع تكرار التنفيذ، وتسجل الأجهزة التي استلمت الإشعار لتجنب إعادة الإرسال لها. انتهاء اشتراك الجهاز يحذفه تلقائياً. نجاح الحفظ لا يتحول إلى خطأ للزائر إذا فشل الإشعار.

الإشعار لا يكشف رقم الزائر أو نص رسالته على شاشة القفل؛ التفاصيل داخل صندوق الرسائل المحمي. تسجيل الخروج يوقف اشتراكات ذلك الأدمن ويلغي جلساته على الأجهزة الأخرى. إيقاف إشعارات هذا الجهاز يؤثر على الجهاز الحالي فقط.

يدعم النظام عدة حسابات إدارة وعدة أجهزة لكل حساب. تصل إشعارات الرسائل الجديدة لكل الأجهزة المشتركة التابعة لحسابات إدارة نشطة وغير معطّلة. إضافة بريد أو دور إدارة وحده لا تسجل الجهاز؛ كل أدمن يسجل الدخول ويفعّل إشعارات أجهزته بنفسه. هذه إشعارات Web Push وليست رسائل بريد إلكتروني.

محاولات الإشعار تنتهي بعد 24 ساعة لتجنب إرسال إشعارات قديمة لاحقاً؛ الرسالة الأصلية تبقى في صندوق الإدارة. وصول الإشعار يعتمد على وجود جهاز مشترك وعلى تشغيل جدولة إعادة المحاولة للأخطاء المؤقتة.

الإشعارات تتطلب HTTPS في الإنتاج، مع استثناء localhost للتطوير. على iPhone يلزم إضافة الموقع إلى الشاشة الرئيسية وفتحه منها ثم السماح بالإشعارات. التسليم يتأثر باتصال الجهاز وإعدادات النظام، ولا يمكن ضمان إشعار فوري عند إيقاف المتصفح أو الجهاز بالكامل. المراجع: [Next.js PWA](https://nextjs.org/docs/app/guides/progressive-web-apps)، [Firebase server credentials](https://firebase.google.com/docs/admin/setup).

## Integration Checks

اختبارات الوحدات تشمل اختيار اللغة، التحقق من الأرقام العربية، الصلاحيات، نطاقات خدمة Push المسموحة، أخطاء الحفظ وإعادة الإرسال، وتشغيل Service Worker دون نافذة مفتوحة.

لتشغيل اختبارات المتصفح مع قاعدة بيانات محلية مستقلة (يلزم Java 21 وFirebase CLI وChrome):

```bash
firebase emulators:start --only "auth,firestore" --project demo-originalcompany
npm run test:e2e
```

Playwright يشغّل نسخة اختبار على المنفذ 3101 ببيئة `demo-originalcompany` وملفات بناء منفصلة في `.next-e2e`. ينشئ حسابات وبيانات اختبار محلية فقط ويختبر دورة إدارة المنتج، تعديل المحتوى والفروع والإعدادات، البحث والفلاتر وشكل المنتجات، التحقق من البريد وحفظه، صندوق الإدارة، منع غير الأدمن، تبديل اللغة وRTL/LTR والموبايل. اختبارات مكتبة الصور تستخدم بيانات صور حقيقية وSDK وهميًا، ولا ترفع إلى Supabase الفعلي. اختبار وصول Push إلى جهاز حقيقي يحتاج إعداد السيرفر واشتراك جهاز بإذن المستخدم.

فحص حي اختياري لأول إعداد: `node --import tsx scripts/verify-live-contact.mjs --confirm-live-test`. يحتاج تشغيل التطبيق المحلي على المنفذ 3000 ببيانات المشروع الحقيقي. يرسل رسالة اصطناعية واحدة من المتصفح ويتحقق من البريد ورقم الهاتف وطلب الإشعار ثم يحذف بياناته فقط. يرفض التشغيل عند وجود أجهزة Push مشتركة حتى لا يرسل إشعارات تجريبية لها. لا يدخل ضمن الاختبارات التلقائية ولا ينشئ حساب أدمن.

فحص رفع الصور الحي: `npm run test:media:live -- --confirm-live-test`. يرفع نسخة اختبار من `ogm.jpg` في مسار فريد، ويتحقق من بيانات Firestore ومن تطابق بايتات الصورة العامة، ثم يحذف النسخة وسجلها فقط. لا يربط الصورة بمنتج أو قسم ولا يستبدل أي صورة موجودة.
